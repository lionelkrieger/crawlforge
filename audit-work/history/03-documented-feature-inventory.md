## 5. Explicitly future / planned (NOT current gaps)

From FS-CRAWL-001 §15 "Open Scope Decisions" (reproduced verbatim in `architecture\07-quality-and-verification\02-open-scope-decisions.md`; the guide's README confirms these are deliberately undocumented as available features — "Where a capability is reserved for a future product decision (for example, unattended headless execution or third-party data enrichment), it is not documented as an available feature"):

1. **Unattended/headless execution** — starting audits from a command line without opening any window ("Not a headless command line", `scheduled-audits.md`). Not in this version.
2. **Manual product-update path** — a local, user-initiated update installation mechanism. "No update checking of any kind exists in this version."
3. **Third-party search/analytics/backlink data enrichment** — importing the user's own search-console/analytics/backlink data (incl. optional **CWV field-performance data enrichment**, spec §7.11) using user credentials. Deliberately left to the product owner.
4. **AMP analysis** — Accelerated Mobile Pages discovery/validation. "Not required by this version."
5. **Raw-SQL administration tool** — direct local-DB query interface (the query builder is already specified). "Not required by this version."

Note: the build plan (`buildplan/index.yaml`) marks all 8 phases, 43 workpieces, and acceptance criteria #1–#48 **completed** — the build plan itself declares no future features. Everything else marked "optional" in the specs (MCP server, export destinations, external DB provider, semantic pipeline, sentiment, stealth profile, render-resolution policy, JS snippets, sample mode, signed access) is **shipped-but-off-by-default**, not future — treat these as current-surface expectations when they are documented to users.

## 6. Observations (complications for cross-inventory key matching)

1. **Heavily overloaded names.** `waf-blocks` is simultaneously a REST path (`/api/audits/{id}/waf-blocks`), a hub event, a metric key, an export dataset, and an MCP resource; `host-throttle` is a hub event, a metric key, and an MCP resource; `waf-block-rate` is both a rule key and a metric key; `redirect-matrix` is a metric key, an export dataset, and part of two REST paths; `ngram-analysis` (MCP) vs "N-Gram Explorer" (UI) vs `/ngrams` (REST). Matching keys across the three inventories will need a namespace disambiguation rule (e.g. `api.rest.*`, `api.hub.*`, `api.mcp.*` suffixes).
2. **Three names for overlapping single-URL actions.** "Single-page analysis" (`POST /api/analysis/single-page`, Single-Page Analyzer window), "URL checker" (`POST /api/tools/url-check`), "Render tester" (`POST /api/tools/render-test`), and the MCP tool `analyze-single-page` overlap heavily (WAF verdict reported in all of them; the finder picker lives in two of them). Gap matching must decide whether these are one capability with four surfaces or four capabilities.
3. **Guide-only API promises.** `GET /api/schedules` and the `local-notification` hub event exist only in `scheduled-audits.md` — absent from FS-CRAWL-001 §10.2/§10.3 and FS-CRAWL-002 Appendices B/C. If the API inventory was built from the specs alone, these will look like UI-vs-API gaps when they are actually spec-vs-guide documentation drift (and vice versa).
4. **The plugin system is spec-complete but guide-thin.** FS-CRAWL-002 §6 defines manifest fields, hook names (`onLoad`, `onTabActivate`, `onDataUpdate`, `onCrawlComplete`, `onTabDeactivate`, `onUnload`), the host context API, permission grants, and `/api/plugins*` routes; the user guide mentions plugins only in passing (startup scan, directories, isolation, Spotlight commands, plugin tabs, blocked requests). A UI inventory may under-report plugin surfaces relative to the spec baseline.
5. **Naming inconsistencies and vocabulary drift.** The schedule recurrence field is named `cron` but explicitly "is not cron syntax"; "scope" means two different things (crawl scope vs content scope — the guide flags this); the product name appears as both "CrawlForge" (guide/docs) and "Crawlforge" (workspace); verdicts for the migration matrix are both "findings" (rule keys with a Pass severity — unusual vs the finding model's Error/Warning/Notice/Pass) and a separate "five-tier verdict system"; the log bot catalogue splits Googlebot into Smartphone/Desktop while the GEO agent catalogue does not (two distinct catalogues sharing purpose vocabulary `search`/`ai-search`/`ai-training` vs `search-index`/`ai-rag-citation`/`llm-training` — the purposes do not map one-to-one).
6. **Overlapping comparison/preview capabilities.** Audit comparison vs content comparison (host-mapped) vs matrix verdict evidence all compare "old vs new"; re-audit-with-refresh vs a new audit vs sample-crawl produce similar-looking surfaces with different semantics — inventories should key these distinctly (`audits.comparison`, `audits.content-comparison`, `crawls.migration-matrix`, `audits.reaudit`, `crawls.sample-mode`).
7. **Spec-only promises at risk of being missed.** Sentiment scoring and `saved_views` filter presets appear only in FS-CRAWL-001; if the UI/API inventories were built from the user guide + extensions doc they may show as "documented but absent" gaps — check against §4.2 before filing.
