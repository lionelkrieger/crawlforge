## 1. Method & join rules

### 1.1 Three-column join

Each capability is joined across three columns — **docs promise** (03) ↔ **UX surface** (02) ↔ **API exposure** (01) — by:

1. **Dot-slug capability key** (shared convention, e.g. `audits.start`, `tools.url-check`).
2. **Exact wire names** where keys diverge: REST `METHOD /path` templates, hub event/method wire names (`crawl-progress`, `Unsubscribe`), MCP tool/resource/prompt names (`start-audit`, `crawlforge://audits/{auditId}/summary`), Electron IPC channel names (`crawlforge:hydrated`).
3. **Route-key equivalence**: 02's `contracts/api/routes.ts` keys (108) are mapped 1:1 onto 01's REST action rows by literal method+path (verified by full read of `app/src/frontend/src/contracts/api/routes.ts`).

### 1.2 Surface-suffix disambiguation (overloaded names)

### 1.3 Guide-only promises

03 §4.1 flags two guide-only promises (`GET /api/schedules`, hub `local-notification`). Rule: a guide-only promise counts as **documented** (the guide is a promise surface) but is tagged `guide-only` and, when the drift is spec-vs-guide rather than code-vs-docs, the finding is filed as documentation drift (G5) rather than a missing capability. **Verified outcome**: both guide-only promises are implemented server-side (see G5-05) — the drift is on the contract/consumer side.

### 1.4 One-vs-four ruling: single-page analysis vs URL checker vs render tester vs MCP `analyze-single-page`

**Ruling: ONE capability ("ad-hoc single-URL inspection") with FOUR surface bindings — not four capabilities.**

- The four overlap heavily by promise and implementation: all report a WAF verdict, all return findings over one URL without a project; `analysis.singlePage` and `tools.urlCheck`/`tools.renderTest` share the finding model and (in two of them) the finder selector picker (02 rows `tools.single-page-analyzer`, `tools.single-page.render-inspect`, `tools.render-tester`, `tools.url-check`; 03 Obs. 2). The MCP tool `analyze-single-page` is documented as a 1:1 projection of `POST /api/analysis/single-page` (03 `automation.mcp-tools`; `McpToolSurface.cs:10-17` (verified): "all eight lifecycle tools, each mapped one-to-one onto the corresponding local API operation").
- **Accounting rule for this register**: the capability is counted **once** in the coverage matrix (Tools domain, ✓ reachable — the tools bench mounts Single-Page Analyzer, URL Check and Render Tester, verified in 02 §2 and re-checked: the three route keys `analysis.singlePage`, `tools.urlCheck`, `tools.renderTest` all have mounted callers). No G1 "dark" row is filed for any of the four, because the *capability* is reachable.
- Residual differences that remain real and are filed elsewhere: (a) MCP exposes only the single-page variant — no `url-check`/`render-test` MCP sibling — classified **intentional** per §11.1 lifecycle-only tool scope (G6-03); (b) the three REST ops stay distinct in the API column (different payloads: render-test returns screenshot/DOM/console; url-check returns redirect chain/headers) — any future dedup must not merge the wire contracts.
