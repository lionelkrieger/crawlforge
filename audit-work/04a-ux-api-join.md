## 1. Method & join rules

1. **Join keys.** (a) dot-slug capability keys as emitted by inventories 01/02 (routes.ts keys, tool-screen slugs); (b) **exact wire strings** — REST `METHOD /path/template` literals compared against controller `[Route]`/`[Http*]` attributes and minimal-API `MapGet/MapPost` calls; SignalR method names (`Subscribe`/`Unsubscribe`) and the 19 catalogued server event names vs the frontend hub contract; MCP tool/prompt/resource names vs `McpToolSurface`/`McpPromptSurface`/`McpResourceSurface`; Electron IPC channel names in `preload/bridge.ts` + `preload.ts` vs renderer consumers.
2. **Darkness test (A1).** A capability is dark when the *only* references to its route key/name anywhere in `app\src\frontend\src` are the declarative catalogs (`contracts/api/routes.ts`, `contracts/api/contracts-map.ts`) — i.e. zero invocation from any surface, store action, tool, or the renderer at large. All 46 Section-A keys were re-grepped individually (batched) and all confirmed dark; the one nuance is `metrics.get` (also named in `app\src\frontend\src\store\apiClient.ts:141` raw-response plumbing, still never invoked — §5.2).
3. **Affordance test (A2).** A UX affordance is dark when it renders/advertises/promise-links a capability whose backing surface is unmounted, unwired, or nonexistent. Sub-classes: **complete-but-unmounted** (working, route-wired component with no mount point), **partial** (some backing exists but the chain breaks), **copy-only** (text promises a screen/action that does not exist).
4. **Drift test (A3).** routes.ts (`contracts/api/routes.ts`, 108 operations, header claims "the complete route surface") is compared operation-by-operation against the 114 backend REST actions of inventory 01 (111 controller actions verified via attribute grep + 3 minimal-API mappings in `CrawlForgeBackend.cs:125-135`). Also: hardcoded literal route strings outside the catalog, name collisions across channels, and wire conventions that the frontend type declarations misdescribe.
5. **Count reconciliation (both directions close exactly).**
   - REST: 114 backend actions − 108 routes.ts rows = **6 endpoints with no contract row** (A3-01): `GET /api/exports/{id}`, `POST /api/destinations/{id}/deliver`, `GET /api/schedules` (cross-project), `POST /api/system/shutdown`, `GET /api/diagnostics/version`, `GET /hub`. All 108 catalog rows were matched 1:1 to a controller template (segment-identical modulo ASP.NET `{id:long}` constraint syntax vs `{id}`).
   - UX: 108 route keys − 62 with callers = **46 dark keys** (Section A of 02), all re-verified here; they are covered one-for-one by A1-01…A1-14 (9+3+2+4+4+2+2+6+4+3+1+1+1+4 = 46).
   - Hub: backend catalog = 2 client→server methods + **19** server→client events (`HubEventCatalog.cs`); frontend contract = 2 + **18** (`contracts/hub/events.ts:316-333`, `store/hubDemux.ts:127-293`). Delta = `local-notification` (A1-15 / A3-03).
   - Electron: 11 IPC channels (9 typed + `crawlforge:get-bridge` + `crawlforge:hydrated`); renderer consumes exactly 1 (`get-bridge` via `window.crawlForge`, `App.tsx:24`).
6. **Severity rubric.** critical = the product's primary user outcome has zero reach in the shipped shell; high = a named product domain or core lifecycle verb is unusable from the UI; medium = meaningful capability/contract loss with workarounds or narrow scope; low = benign duplication, by-design API-only, or cosmetic drift.
