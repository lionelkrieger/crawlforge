## Rationale

The first build shipped working engines behind screens that were never mounted: of 16 baseline report surfaces, 10 had no component and the rest were never mounted (UNDERBUILD-AUDIT). The specification described surfaces but never bound each capability to a reachable place in the UI, so nothing failed when a capability was backend-only. D-018: every feature must be bound to a reachable place in the UI.

## Proposed text: new file `06-frontend-shell-and-ui/04-ui-surface-map.md`

### 2. Capability bindings

- Every in-scope capability has a binding with three columns: **Configure** (where it is switched on or set up), **Trigger** (how it is run) and **View** (where its results appear), each naming surfaces from §1 or `-` where not applicable.
- A capability may be **exempt** only when it is delivered solely through the local API or MCP; exempt capabilities are listed with that reason, and their invocations are visible in the MCP action log (UI-21).
- The binding table is part of this file and is maintained through change records like any other specification text.
- Every view binding must reach the actual data: a surface that renders a placeholder or empty frame does not satisfy a binding.

### 3. Verification

- `check_traceability.py` fails when an in-scope capability has no binding and no exemption, when a binding names a surface not in §1, or when a surface in §1 is bound by no capability (dead surface).
- **Acceptance (amends `03-fixture-site.md` §2):** for every capability with a UI binding, end-to-end acceptance includes reaching it through its navigation path in the running product (configure, trigger and view as bound). A capability whose bound surface is not reachable is not complete, whatever its backend tests show.

## Proposed binding table

See `CR-018-bindings-draft.md`: 246 bindings generated from the architecture traceability tags and a per-section binding table, with per-capability overrides where one section covers several surfaces, plus 5 exemptions (API access, structured JSON for agents, website overview, change analysis, machine-readable findings: all MCP or API only).

## Open questions

1. Is the surface catalogue complete and are the navigation paths right (for example Clients on the main hub, Logs under the project)?
2. Configuration editor tab list and order.
3. Review of the generated bindings: spot-check any capability; corrections are cheap now.
4. Should a maximum click depth from the main hub be prescribed (for example every view surface within three clicks)?

## Impact

The build-plan extension gets one UI workpiece per surface, each citing the capabilities bound to it, and acceptance walks each navigation path. The frontend can no longer ship a capability without a mounted place for it.
