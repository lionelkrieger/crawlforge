## Rationale

D-002: the headless browser is driven directly through the Chrome DevTools Protocol (CDP), replacing a third-party automation library, for precise control of network capture, waits, emulation, blocking and caching. §5.6 is technology-neutral; this CR fixes the control interface and its required behaviours.

## Proposed text

**New §5.6.2 Rendering control layer:**

> - The headless browser is controlled directly through the **Chrome DevTools Protocol**. No third-party browser-automation library sits between the engine and the browser.
> - **Process model:** a bounded pool of long-lived browser processes; each page is rendered in a **fresh browser context** (isolated cookies, storage and cache, except the audit-scoped shared resource cache below). Pool size obeys the limits resolver (section 4) and the global concurrency cap.
> - **Network capture:** request and response events (URL, method, status, headers, timing, size, initiator) feed the network-waterfall summary (section 5.6), WAF evaluation (FS-CRAWL-002 §2) and analytics/consent inspection (FS-CRAWL-002 §14.2).
> - **Console and runtime exceptions** are captured per page.
> - **Emulation:** device, viewport, user agent and locale are applied per configuration ("crawl as" presets, CR-012).
> - **Wait rule:** a page is complete when the DOM has been stable and the network quiet for a configured interval, subject to a hard cap. Fixed delays are not used.
> - **Resource blocking** is part of the configuration profile (fonts, media, third-party scripts). A tracking/consent profile blocks nothing.
> - **Shared resource cache:** static resources are cached for the duration of one audit so each site bundle is fetched once.
> - **Service workers** are bypassed for every render (CR-009).
> - Infinite-scroll expansion, the stealth profile, custom JavaScript snippets (section 7.17) and the Core Web Vitals lab probe (section 7.11) run on this layer.
> - The engine supplies the rendered document to the audit pipeline in full audits, not only in single-page analysis.

**§5.9, current text** describing rendered traffic routed through the local intercepting proxy remains, with this addition: "When the rendering control layer captures network events directly (section 5.6.2), routing rendered traffic through the intercepting proxy is optional."

## Open questions

1. Default pool size and context reuse limits.
2. Wait rule defaults: quiet interval and hard cap values.
3. Default resource-blocking profile for SEO audits.
4. Keep the intercepting proxy for rendered traffic at all, or retire it for rendering?

## Impact

Replaces the current rendering pool implementation. The rendered-document handoff fixes the confirmed underbuild that full audits never render. Fixture traps: JS-only content, client-side redirect, service worker, consent banner (CR-015).

## Resolutions (owner, 2026-11-17)

1. Pool size: **half the logical processors, minimum 2, configurable**.
2. Wait rule: **500 ms quiet, 20 s hard cap**, both configurable.
3. Resource blocking default: **none**; opt-in "fast" profile.
4. Intercepting proxy: **not used for rendered traffic**; kept as an optional feature for non-rendered traffic.

Applied with these resolutions. Where the applied text differs from the proposed text above, the applied text in the architecture is authoritative.
