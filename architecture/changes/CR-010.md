## Rationale

Consent banners can cover content and hold back scripts until interaction, changing both content and tracking results. FS-CRAWL-002 §14.2 inspects dataLayer and Consent Mode v2 in rendering mode but does not control the consent state.

## Proposed text

> **§14.2.1 Consent states.** In rendered capture a configuration selects one or more consent states: **no interaction**, **consent accepted**, **consent rejected**. Known consent platforms are operated by built-in selectors; a custom selector may be configured for others. When more than one state is selected, each URL is rendered once per state, and the tags, requests, cookies and dataLayer events observed in each state are stored and compared. Tags that fire, or cookies that are set, before consent is given are reported as findings.

## Open questions

1. Which consent platforms get built-in selectors in the first version?
2. Multi-state rendering multiplies render cost: limit to a sample of URLs by default?
3. Does content analysis use the "no interaction" render, the "accepted" render, or a configured one?

## Impact

Depends on CR-006. Fixture trap: consent banner with a tag firing before consent (CR-015).

## Resolutions (owner, 2026-11-17)

1. Built-in platforms: Cookiebot, OneTrust, CookieYes, Complianz, Agency Support Consent; custom selector for others.
2. Multi-state rendering on a sample by default (about 20 URLs or one per pattern), full crawl optional.
3. Content analysis uses the no-interaction render.

Applied with these resolutions. Where the applied text differs from the proposed text above, the applied text in the architecture is authoritative.
