# CR-016: Out-of-scope records (email reports, webhooks, multi-user)

| Field | Value |
|---|---|
| Type | amendment |
| Status | draft |
| Decisions | D-006, D-013, D-009 |
| Capabilities | CAP-H-189, CAP-H-187, CAP-H-191 |
| Target | `01-foundation-and-governance/01-clean-room-and-exclusions.md` (new §1.5 Product scope exclusions); `06-frontend-shell-and-ui/02-virtualization-and-explorers.md` §8.5 |

## Rationale

D-006: email reports are not needed. D-013: webhooks are not needed; MCP covers the use case. D-009: single user per desktop install. §8.5 currently specifies a "notification webhook" destination class, which D-013 removes.

## Proposed text

**New §1.5 Product scope exclusions (owner decisions):**

> | Capability | Status | Decision |
> |---|---|---|
> | Email reports | Not in scope | D-006 |
> | Webhooks and notification webhook destinations | Not in scope; MCP status and completion (section 11.5) covers the use case | D-013 |
> | Multi-user access and permissions | Not in scope; one user per desktop install | D-009 |

**§8.5, current text:** "Destination classes: a cloud drive/spreadsheet service, an object-storage endpoint, and a notification webhook — all addressed with the user's own credentials, never vendor accounts."

**Replacement:** "Destination classes: a cloud drive/spreadsheet service and an object-storage endpoint, addressed with the user's own credentials, never vendor accounts. Notification webhooks are out of scope (section 1.5)."

## Open questions

1. The register shows implemented destinations as local folder, FTP and SFTP, which differ from the specified classes. Should §8.5 be amended to match what was built, or should the build follow the spec? (Register step 2 will record this as a finding.)

## Impact

Removes webhook delivery from any build-plan extension.
