## Rationale

§2.6 limits outbound traffic to crawl targets, user-configured export destinations and a user-configured database. D-005 (GSC, GA4) and D-012 (PageSpeed Insights) require user-connected Google APIs; D-010 requires a way to obtain new releases. §2.6 already treats the user's own destinations and database as "the user's own services, not vendor services"; this CR extends that principle. §15 items 2 and 3 recorded exactly these questions as open; they are now resolved.

## Proposed text

**§2.6, current bullet list (unchanged) gains two bullets after the database bullet:**

> - Connections to **user-connected search and analytics services** (Google Search Console, Google Analytics 4, PageSpeed Insights; section 08-integrations), using the user's own OAuth client or API key, only for properties the user has explicitly connected to a project, and only when the user initiates a sync or has scheduled one. None is connected by default.
> - A **user-initiated release check** against the project's public release channel (section 09-distribution). It runs only when the user requests it; it transmits no identifier, usage data or diagnostic data.

**§2.6, current sentence:**

> There is no telemetry, no remote crash reporting, no update checking, no account service, and no vendor-operated cloud service of any kind. User-configured destinations and database servers are the user's own services, not vendor services.

**Replacement:**

> There is no telemetry, no remote crash reporting, no automatic update checking, no account service, and no vendor-operated cloud service of any kind. User-configured destinations, database servers and user-connected search and analytics services are the user's own services, not vendor services. Data synced from them is cached locally so audits and reports remain fully functional offline after a sync. Disconnecting all such services and deleting all destinations restores the guarantee of zero non-crawl outbound traffic, except a release check the user explicitly starts.

**§15 item 2** is replaced by: "**Resolved (CR-003, CR-014, D-010):** a user-initiated release check and manual update installation are in scope; no automatic update checking exists."

**§15 item 3** is replaced by: "**Resolved (CR-003, CR-013, D-005, D-012):** the user's own Google Search Console, Google Analytics 4 and PageSpeed Insights data are in scope through user-connected integrations. Backlink-provider enrichment remains out of scope for this version."

## Traceability

§2.6 gains `> Capabilities: CAP-H-181, CAP-H-182, CAP-H-183` with `Decisions: D-005, D-012, D-010`.

## Open questions

1. Is backlink-provider enrichment explicitly out of scope (as proposed), or left open?
2. Should a release check be offered at all before the first public release, or only once a release channel exists?
3. Exact wording of "release channel" depends on CR-014 (for example GitHub Releases).

## Impact

Excluded-subsystem rows 6 and 7 in §3 are unaffected (no telemetry; release check is not account-bound). Acceptance criteria asserting zero non-crawl outbound traffic must be re-read against the new exceptions (CR-015). Network-audit tooling in `app/tools/network-audit` must allow-list the new endpoints only when connected.

## Resolutions (owner, 2026-11-17)

1. Backlink-provider enrichment: **out of scope** for now; may be proposed later in its own CR.
2. Release check: **specified now, built once public releases exist**.
3. Release channel: **GitHub Releases** (CR-014).

Applied with these resolutions. Where the applied text differs from the proposed text above, the applied text in the architecture is authoritative.
