## Rationale

D-001: both JS and non-JS crawls are required, as first-class modes for every project and configuration. §5.6 currently treats rendering as optional and selectable per audit or URL pattern, without dual or adaptive capture.

## Proposed text

**§5.1, current row:** `| Rendering mode | No | Plain HTTP fetch, or JavaScript-rendered fetch (section 5.6) |`

**Replacement:** `| Capture mode | No | Non-JS, JS, dual or adaptive capture (section 5.6.1); defaults to non-JS |`

**New §5.6.1 Capture modes:**

> A configuration selects exactly one capture mode:
>
> | Mode | Behaviour |
> |---|---|
> | Non-JS | Every in-scope URL is fetched over plain HTTP and parsed without executing scripts. |
> | JS | Every in-scope URL is rendered in the headless browser (section 5.6); the post-render document is the analysed document. |
> | Dual | Every in-scope URL is captured both ways. Both documents are stored; the response-vs-rendered comparison (section 7.18) is computed for every URL. |
> | Adaptive | Every in-scope URL is fetched over plain HTTP. A sample of URLs per template or URL pattern is also rendered and compared on SEO-relevant elements (links, title, meta description, canonical, meta robots, headings, word count, structured data). Where rendering materially changes any of these, the pattern switches to rendered capture for the rest of the audit. Each switch is recorded with its evidence and reported as a "JavaScript-dependent template" finding. |
>
> - Per-URL-pattern overrides (section 5.6) apply on top of any mode.
> - Every URL record states which capture produced it (raw, rendered, or both).
> - Report surfaces and exports show the capture source per record; comparison views are available whenever both captures exist for a URL.
> - Custom extraction (section 7.9) and custom search (section 7.16) can target the raw document, the rendered document, or both, when both exist.

## Open questions

1. Adaptive mode: sample size per template or pattern, and how templates are identified before template identification exists (CR-017 E-128). Proposed fallback: group by URL path pattern.
2. Adaptive mode: the threshold for a "material" change per element (for example any difference in canonical or meta robots, but what difference in word count?).
3. Default mode for new configurations: non-JS (proposed) or adaptive?
4. Storage cost of dual mode on large sites: any cap or warning?

## Impact

Schema: URL records gain a capture-source field; rendered and raw document storage in the content store (§9.6). REST/MCP: capture mode in configuration contracts and URL detail. UI: configuration editor (CR-012) and explorer columns. Acceptance: fixture traps for JS-only links and late meta changes (CR-015).

## Resolutions (owner, 2026-11-17)

1. Adaptive sampling: **group by URL path pattern, 3 to 5 URLs per group**, with the sample size configurable and a **manual per-pattern capture override** in the configuration.
2. Material change: **any difference in title, canonical, meta robots or hreflang; a different set of links; or a word-count change above 20%** (configurable).
3. Default mode: **non-JS**, reviewed once adaptive mode passes acceptance on the fixture site.
4. Dual-mode storage: **warning above a threshold, no hard cap**.

Applied with these resolutions. Where the applied text differs from the proposed text above, the applied text in the architecture is authoritative.
